# 微博动态长列表

仅在微博底栏「消息」里的「动态」页，列表加载后读树慢、任务只需作者 / 动态文字 / 时间时使用。不是首页推荐流、私信列表或动态详情的通用参数；全局默认仍为 50。

- 可用 `pua_observe(mode="tree", snapshot_max_depth=17)`。文字通常在 `StaticText.value`，其 name 可能只有 `WBTimelineAttributedTextView`；不要只读取 label，也不要用相同 name 合并不同内容。
- 本次实测 17 是保留动态文字的最低档；16 保留空 Cell，却丢掉作者、正文和时间，不能用于读动态。14 及以下连列表行也缺失。
- 17 会省略图片 / 头像子节点、部分更多操作按钮等；需要图片内容、图标状态、操作入口或所需文字缺失时，取截图并以 50 重读。仅凭文字一致不能声称所有上下文完整；动态预览也不代替全文详情。
- 只在本次独立观察指定深度，成功后恢复 50。动作后观察、selector 查询、列表采集仍默认 50；不直接改共享原生会话设置。
- 原生树包含大量离屏行，顶部曾把很多离屏文字当成视口内节点返回；不能凭节点数量或坐标推断全量、可点击、已到底。按截图核对可见内容和滚动范围。系统通知浮层可能临时使前台变为 SpringBoard，应排除该轮，而不是拿通知树对比微博。

## 实测边界

2026-10-12，当前真机 iPhone 17 Pro Max，PUA 0.3.12，children 不限制、昂贵可见性查询关闭。动态页首次取树约 0.52–1.43 秒，继续加载后 50 超过 4 秒；稳定在 261 个 Cell 后交替测量：

| 页面位置 | 50：source 中位数 | 17：source 中位数 | 降幅 |
| --- | ---: | ---: | ---: |
| 顶部，3 次 / 档 | 7.55 秒 | 5.62 秒 | 约 26% |
| 滚动后，2 次 / 档 | 2.32 秒 | 1.47 秒 | 约 37% |

顶部每档 3 次包含一组早期稳定对照；单独后续两次 / 档的降幅约 29%。两处 50 / 17 原始 StaticText 均为 872 个，type / label / name / value 的多重集合一致，Cell 均为 261 个；17 将原始节点由约 4,326 减到 2,131。只说明这两处的文字保留，不保证其他版本、详情或图片上下文。

17 仍可能超过 4 秒，20 / 24 没解决本次慢列表。整次工具调用还包括前台、视口、设置等请求；新 Runtime 首次调用在本次常比单个 source 慢很多，不能把 source 提速等同于整段任务等比例提速。页面位置和缓存会改变时间，即使节点数一样也不能承诺固定耗时。
